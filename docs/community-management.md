# 社区管理框架

本文件定义 dsh-TUI 的公开社区协作方式。它负责回答“社区如何提出、讨论、跟踪和交付工作”，不替代 [贡献指南](contributing.md)、[行为准则](../CODE_OF_CONDUCT.md) 或安全报告流程。

## 目标

- 让用户知道项目当前优先解决什么问题。
- 让贡献者知道从哪里提出想法、如何获得确认、怎样证明完成。
- 让维护者能控制范围、风险和兼容性，而不是靠临时口头决定。
- 让每项公开工作都能追溯到 Discussion、Issue、PR 和验证结果。

## 公开入口

| 入口 | 用途 | 产出 |
| --- | --- | --- |
| Bug 表单 | 可复现的错误、崩溃、回归 | Bug issue |
| Discussions Ideas | 新功能、行为变化、交互改进 | Proposal；认可后建立 tracking issue |
| Discussions Q&A | 安装、配置、使用问题 | 可复用的答案或文档修复 |
| Discussions Show and tell | 插件、主题、周边项目和案例 | 社区展示与生态记录 |
| Roadmap tracker | 公开工作的状态、负责人、依赖和验收条件 | 可追踪的任务表 |
| Pull Request | 已获得入口确认的具体实现 | 可审查、可验证的改动 |

入口分流与当前仓库规则保持一致：功能建议不直接以 issue 代替提案，bug 不要求预先批准，代码 PR 应关联对应 issue。详见 [贡献指南](contributing.md)。

## 角色

| 角色 | 责任 |
| --- | --- |
| Maintainer | 确定项目范围、接受或拒绝公开提案、维护 roadmap、做最终合并决定 |
| Area owner / PIC | 负责某个工作流或模块的推进、更新状态、组织验证和交接 |
| Reviewer | 检查设计、行为、兼容性、测试和文档，不默认承担实现责任 |
| Contributor | 提交复现、文档、测试、修复或经过确认的功能实现 |
| Community member | 提供使用反馈、案例、问题背景和方案讨论 |

PIC 只有在实际有人负责时才填写。没有负责人和退出条件的事项只能停留在 `Design` 或 `Not started`，不能伪装成进行中。

## 提案流程

```text
用户问题或想法
  -> Discussion / Bug report
  -> 维护者澄清范围与价值
  -> 接受 / 暂缓 / 拒绝
  -> Tracking issue
  -> 设计、实现、验证
  -> PR review
  -> 合并与 release note
  -> Roadmap 状态更新
```

### 接受提案的最低信息

- 谁遇到这个问题，场景是什么；
- 当前行为和期望行为；
- 为什么应由 dsh-TUI 解决，而不是由 DSH 或外部插件解决；
- 影响哪些用户、平台或兼容版本；
- 如何验证完成；
- 是否需要新的公开 API、配置或持久化格式。

提案被接受不代表实现方案已经确定。实现前仍需要在 tracking issue 中写清范围、非目标、依赖和退出条件。

## Roadmap 规则

公开 roadmap 只收录满足以下条件的事项：

1. 对用户、贡献者或生态有可解释的价值；
2. 有明确结果，而不是“继续优化”“提升体验”这类模糊描述；
3. 能拆成一个或多个可跟踪的 Issue；
4. 有 PIC，或明确标记为等待认领；
5. 有验收条件和依赖关系；
6. 能说明为什么现在做，以及为什么不是 Future Work。

每个 roadmap task 至少包含：

| 字段 | 内容 |
| --- | --- |
| Task | 一个用户可理解的结果 |
| PIC | 当前负责人；没有则写 `TBD` |
| Issue | 讨论和范围的唯一跟踪入口 |
| PR | 实现入口；未开始时写 `-` |
| Status | 使用统一状态标记 |
| Depends on | 前置任务或外部条件 |
| Exit criterion | 判断完成的证据 |

Roadmap 是状态面，不是承诺所有事项都会按顺序完成。维护者应在范围变化、阶段完成、任务延期或任务被拒绝时更新它。

## 状态标记

| 状态 | 含义 |
| --- | --- |
| `✅ Done` | 已合并，并且完成了适用的验证 |
| `🚧 In progress` | 已有负责人，正在实现或验证 |
| `🟡 Design` | 方向进入讨论，但实现范围尚未冻结 |
| `⚪ Not started` | 已确认属于公开方向，但尚未开始 |
| `🧪 Experimental` | 可试用，接口或行为不作稳定承诺 |
| `⏸ Deferred` | 暂缓，不进入当前阶段关键路径 |
| `❌ Rejected` | 已讨论并决定不做，保留理由 |

状态变化应在 tracking issue 留下简短原因。只把 PR 已合并称为 `Done`，不要把“有人提出”或“代码已开分支”当作完成。

## 维护节奏

建议采用以下节奏，具体频率可以根据维护者人数调整：

- 定期 triage：处理新 bug、重复问题、无复现问题和提案状态；
- 每次版本发布前：检查 roadmap 任务是否有实际验证证据；
- 每个阶段结束时：更新阶段总结、未完成事项和 Future Work；
- 每次重大设计决定：增加 ADR 或在 tracking issue 中记录决定与替代方案；
- 长时间没有更新的事项：标记为 `Deferred`、重新确认负责人，或关闭并说明原因。

## 决策和冲突处理

- 用户反馈决定问题优先级，不直接决定实现方案。
- PR 讨论聚焦代码和证据，不用个人身份、贡献数量或外部影响力替代技术论证。
- 重大范围变化由 Maintainer 在 tracking issue 中记录最终决定。
- 对行为准则、安全问题和隐私问题，分别走既有的 Code of Conduct 和安全报告渠道。
- 不通过私下口头承诺绕过公开流程；确有例外时，维护者应在对应 issue 留下可公开的范围说明。

## 质量指标

社区健康度优先看这些指标：

- bug 是否能复现、分类和关闭；
- roadmap 任务是否有负责人和退出条件；
- 从提案到决定是否长期没有响应；
- 发布是否包含验证和已知限制；
- 新贡献者是否能通过文档完成一次有效贡献；
- 回归问题是否得到记录并进入后续改进。

Star、PR 数量、commit 数量和单纯的活跃度不作为项目进展的主要指标。
